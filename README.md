## Requirements

### Python

```bash
pip install -r requirements.txt
```

Requires Python ≥ 3.10.

### C++ — build before running the benchmark

> **The C++ binary must be compiled before running `Benchmark.py`.**
> If the binary is not present at `apriori_cumulate/cpp/apriori_cumulate_cpp`, `Benchmark.py` silently skips the C++ implementation and Figure 3 and Tables V and VII will be incomplete.

The C++ pipeline requires [Apache Arrow](https://arrow.apache.org/) with Parquet support. The easiest way is via Conda:

```bash
# Create (or reuse) a conda environment and activate it — $CONDA_PREFIX must be set
conda create -n armmht python=3.11 -y   # skip if you already have an env
conda activate armmht
conda install -c conda-forge arrow-cpp parquet-cpp -y
```

Then build the binary from the repo root:

```bash
cd apriori_cumulate/cpp
make CONDA_ENV=$CONDA_PREFIX apriori_cumulate_cpp
cd ../..
```

On macOS, use Clang:

```bash
cd apriori_cumulate/cpp
make CONDA_ENV=$CONDA_PREFIX CXX=clang++ apriori_cumulate_cpp
cd ../..
```

On a Linux cluster with a module system (e.g. SLURM):

```bash
module load arrow   # or however Arrow is exposed on your cluster
cd apriori_cumulate/cpp
make CONDA_ENV=$CONDA_PREFIX apriori_cumulate_cpp
cd ../..
```

Verify the build:

```bash
ls -lh apriori_cumulate/cpp/apriori_cumulate_cpp
# Expected: a file of a few hundred KB, executable bit set
```

### How the paper runs were executed (UCPH Hendrix cluster)

The SLURM scripts we used on Hendrix are in `slurm/`. They load the cluster's `anaconda3/2024.10-py3.12.7` module (Python 3.12.7) and `gcc/13.2.0`, and expect the repository at `~/benchmark` with the data in `Data/`. Module names and the pinned node (`hendrixgpu07fl`) are specific to Hendrix; adjust them for another cluster.

| Script | What it does | Paper output |
|---|---|---|
| `slurm/build_cpp_intel.sh` | Builds the C++ binary against the Arrow headers bundled with pyarrow (`-O3 -march=native`) and runs a smoke test | none |
| `slurm/run_slurm_benchmark.sh` | Runs `Benchmark.py`; submit with `sbatch --export=ALL,REPEATS=3,RUN_FULL=1 slurm/run_slurm_benchmark.sh` | Tables III–VII, IX, X and Figures 1–9 |
| `slurm/run_full_verify_clean.sh` | Prints dataset statistics for the 100k sample and the full data, then runs Experiment 9 | Tables II and VII |
| `slurm/run_memory_verify_clean.sh` | Measures peak resident memory of every implementation with `/bin/time -v` and writes `time_v_summary.csv` | Table VIII |

Build the binary first with `sbatch slurm/build_cpp_intel.sh`, then submit the other scripts.

## Data

The dataset is published on Zenodo and must be downloaded manually:

**DOI: [10.5281/zenodo.20307389](https://doi.org/10.5281/zenodo.20307389)**

Download the Parquet file from Zenodo and place it in the `Data/` folder (replacing the `Data_here` placeholder):

```
Data/
└── wishlist_data.parquet   ← place downloaded file here
```

The file contains three columns:

| Column | Type | Description |
|---|---|---|
| `wishlist_id` | string | Unique identifier for each wishlist |
| `product_id` | string | Unique identifier for each product |
| `category_name` | string | `>`-separated taxonomy path, e.g. `Clothing > Tops > T-Shirts` |

### Generate samples

```bash
python create_samples.py
```

This reads from `Data/` and writes four size-limited samples to `Data/samples/`:

```
Data/samples/
    5000/
    20000/
    50000/
    100000/
```

To regenerate existing samples:

```bash
python create_samples.py --overwrite
```

To generate specific sizes only:

```bash
python create_samples.py --sizes 20000 100000
```

> **Sampling method:** Wishlist IDs are listed in the order they first appear in the file, and every third ID is kept until N are selected (`all_ids[::3][:N]`). For N = 100,000 the sample therefore comes from roughly the first 300,000 wishlists, about 30% of the file, not from the whole dataset.

## Running the pipelines individually

All scripts take the sample directory as their first argument.

### Python Cumulate

```bash
python apriori_cumulate/python/Apriori_Cumulate_Python.py Data/samples/100000 \
    --k-levels 3 --min-support 0.02 --min-conf 0.6 --min-lift 1.5 \
    --max-ante-len 3 --max-cons-len 2 --max-len 5 \
    --output rules_python.csv
```

### mlxtend Basic (ancestor expansion)

```bash
python apriori_mlx_ancestor/Apriori_MLX_Ancestor.py Data/samples/100000 \
    --mode basic --k-levels 3 \
    --min-support 0.02 --min-conf 0.6 --min-lift 1.5 \
    --output rules_mlx_ancestor.csv
```

### mlxtend Flat

```bash
python apriori_mlx_tend/Apriori_MLX_Flat.py Data/samples/100000 \
    --level leaf \
    --min-support 0.02 --min-conf 0.6 --min-lift 1.0 \
    --output rules_mlx_flat.csv
```

This baseline follows mlxtend's documented `TransactionEncoder -> apriori -> association_rules`
workflow on a single flat taxonomy level. The default `--level leaf` matches
Cumulate's `K=1` item representation and remains invariant as Cumulate varies
`K`.

### C++ Cumulate

Build first (see [C++ — build before running the benchmark](#c----build-before-running-the-benchmark)).

Run (positional args: `<base> <k> <support> <conf> <lift> <max_ante> <max_cons> [output]`):

```bash
./apriori_cumulate/cpp/apriori_cumulate_cpp Data/samples/100000 3 0.02 0.6 1.5 3 2
```

## Reproducing the paper's figures and tables

The commands below reproduce the paper's figures and tables using the parameters behind the published results. Tables I, II and VIII do not come from `Benchmark.py`; see `slurm/` for Tables II and VIII.

- 100k wishlist sample from `create_samples.py --sizes 100000`
- K-sweep: K = 1, 2, 3, 4, 5 · support = 0.02 · conf = 0.6 · lift = 1.5 · max\_ante = 3 · max\_cons = 2
- Support sweep: K = 3 · support ∈ {0.05, 0.03, 0.02, 0.01} · same conf/lift/lengths
- Sensitivity grid: τ ∈ {0.5, 0.6, 0.7} · λ ∈ {1.2, 1.5, 2.0}

**Step 1 — Build the C++ binary** (skip if already built):

```bash
cd apriori_cumulate/cpp
make CONDA_ENV=$CONDA_PREFIX apriori_cumulate_cpp
cd ../..
```

**Step 2 — Generate the 100k sample** (skip if `Data/samples/100000/` already exists):

```bash
python create_samples.py --sizes 100000
```

**Step 3 — Run all benchmark experiments** (all nine experiments; Experiments 6–9 read the full `wishlist_data.parquet` via `--catalogue-base`):

```bash
python Benchmark.py Data/samples/100000 \

    --ssweep-support 0.05 0.03 0.02 0.01 \
    --ssweep-k 3 --ssweep-conf 0.6 --ssweep-lift 1.5 \
    --ssweep-max-ante-len 3 --ssweep-max-cons-len 2 \

```

**Expected rule counts** at the baseline (K=3, support=0.02, conf=0.6, lift=1.5):

| Stage | Count |
|---|---|
| Raw rules | 321 |
| After score+rank (lift ≥ 1.5) | 315 |
| After family dedupe | 315 |
| After antimirror dedupe (final) | 293 |

Final rule counts by K-level: K=1 → 2, K=2 → 242, K=3 → 293, K=4 → 1,150, K=5 → 2,360.

**Output figures** are written to `results/thesis_repro/k_sweep/figures/` and `results/thesis_repro/support_sweep/figures/`.

> **Note:** Runtimes (Figures 3 and 4, Tables V–VII) are wall-clock times from your machine and will differ from the paper's values, which were measured on the UCPH Hendrix cluster. Rule counts (Figures 1, 2, 5 and 6, and the rule columns of Tables V–VII and IX) are deterministic and should match exactly with the same data and parameters.

> **Benchmarking methodology:** Before each timed sweep (Experiments 4 and 5), `Benchmark.py` runs one untimed warmup pass per implementation. This ensures OS page caches are warm and shared libraries (Arrow, Parquet, numpy) are resident in RAM before any measurements begin, so that reported times reflect algorithmic performance rather than cold-start I/O overhead. This is standard practice in systems benchmarking.

## Running all benchmark experiments

`Benchmark.py` runs up to nine experiments in one command, covering all reproducible figures and tables in the paper:

| Experiment | `--skip` name | Paper output |
|---|---|---|
| 1: Sensitivity sweep (τ/λ grid) | `sensitivity` | Table IX |
| 2: Basic vs. Python Cumulate | `basic_vs_cumulate` | Not reported in the paper |
| 3: Example rules at K=5, s=0.02 | `example_rules` | Table III |
| 4: K-sweep (K=1..5, all implementations) | `k_sweep` | Figures 2, 3, 4, 7, 8, 9 + Tables V, XII |
| 5: Support sweep (s varies, K=3 fixed) | `support_sweep` | Figures 5, 6 + Tables VI, XIII |
| 6: L0-to-L0 leaf pair case study | `l0_pair_example` | Industrial illustration |
| 7: Rule-based candidate-space reduction | `rule_candidate_space` | Table XI + Figure 11 |
| 8: Held-out recall evaluation | `held_out_recall` | Figure 12 + Table XV |
| 9: Full-dataset scalability | `full_dataset` | Table VII |

**Experiments 6, 7, and 8 require a product catalogue** passed via `--catalogue-base`. This can be the same merged parquet directory used for `base` (the file must include a `product_id` column), or a directory with `products/` and `categories/` parquet sub-directories. These experiments are automatically skipped with a clear message if the catalogue is not available. Experiment 7 needs a Cumulate rules CSV: pass one with `--candidate-rules-csv`, or run Experiment 3 in the same `--output-dir` and Experiment 7 picks up its K=5 rules automatically. Otherwise it is skipped.
